# 课程设计选题方向与技术降级方案

## 一、选题方向

### 最终选题

**"基于 Spark+Flask 的分布式容器集群资源监控与日志分析可视化平台"**

英文：Container Cluster Resource Monitoring and Log Analysis Visualization Platform based on Spark & Flask

### 选题理由

1. **与现有基础设施天然衔接**：项目已有 Redis、MinIO、Hadoop HDFS/YARN、Gotenberg、FastAPI 等 Docker 容器服务，选题可以直接复用 docker-compose.demo.yml 的编排能力和已有容器资源。

2. **数据源真实可采集**：Docker Engine API 提供实时容器指标（CPU%、内存使用、网络 IO、磁盘 IO、进程数），不需要构造模拟数据集，采集到的数据天然具有"海量""时序""多维"等大数据特征。

3. **完整契合课程五大要求**：

| 课程要求 | 本选题映射 |
|----------|-----------|
| 数据存储与读取（CSV/JSON/HDFS） | Docker Stats API → 定时采集 → CSV/JSON 本地文件 → HDFS 存储 |
| Spark 数据预处理（清洗/转换/统计） | PySpark 读取 CSV → 清洗异常值 → 时间窗口聚合 → 多维统计分析 |
| Flask Web 服务（路由/API/JSON） | Flask 提供 /api/monitor/* 接口，返回监控统计 JSON |
| ECharts 可视化（看板/柱状图/折线图/饼图/表格） | 容器资源仪表盘 + CPU/内存趋势图 + 容器状态饼图 + 资源分布热力图 |
| 附加功能（刷新/交互/轻量化） | 手动刷新 Spark 重算、ECharts 图表交互、docker-compose 一键启停 |

4. **容器集群管理本身就是业务价值**：能直接展示"docker-compose 全局容器启停→采集监控数据→Spark 处理→Dashboard 展示"的完整链路，比纯 CSV 文件处理更有工程价值和展示效果。

5. **论文素材充足**：容器监控是热门赛道（全球市场 2024 年 $17 亿，CAGR 9.1%），开题有行业背景可写。

## 二、市场调研

### 2.1 容器监控市场规模

- **全球容器监控市场**：2024 年 $17 亿美元，预计 2030 年达 $31 亿美元，CAGR 9.1%（来源：Strategic Market Research）
- **开源容器管理软件市场**：2024 年 $21 亿美元，预计 2033 年达 $65 亿美元，CAGR 15.4%（来源：Market Research Intellect）
- **核心驱动因素**：云原生普及（K8s 采用率超 60%）、微服务架构主流化、DevOps 文化渗透、实时可观测性刚需

### 2.2 主流竞品分析

| 竞品 | 定位 | 优势 | 劣势 | 与本项目关系 |
|------|------|------|------|-------------|
| **Prometheus + Grafana** | 行业标准监控栈 | 生态丰富、时序数据库、告警强大 | 部署重（需 Prometheus Server + Node Exporter + AlertManager）、学习曲线陡 | 参考其指标采集思路 |
| **cAdvisor** | Google 容器监控代理 | 原生集成 Docker、自动发现容器 | 仅提供基础指标，无可视化分析 | 参考其容器发现机制 |
| **Portainer** | Docker 可视化管理 | 界面友好、一键部署、支持 Swarm | 偏运维管理、缺乏数据分析能力 | 参考其容器列表展示 |
| **Netdata** | 实时系统监控 | 秒级采集、零配置、美观 | 偏系统级、容器维度弱 | 参考其实时监控 UI |
| **Datadog** | 商业 APM 平台 | 全栈可观测、AI 告警 | 昂贵（$15+/host）、SaaS 依赖 | 非竞品（商业闭源） |
| **本项目** | 轻量级教育监控平台 | 单机部署、数据分析强（Spark）、前后端一体化、教育友好 | 非生产级、规模受限 | — |

### 2.3 本项目的差异化定位

1. **轻量化**：整个系统运行在 MacBook Air 单机上（8 个以内 Docker 容器），无需集群部署
2. **教育友好**：代码简洁、流程清晰，适合课程展示和答辩
3. **分析能力强**：利用 Spark SQL 做多维聚合分析（而非常见的简单平均值），这是 Grafana 等竞品不具备的
4. **一体化**：采集→存储→计算→API→可视化，全流程自研，不依赖第三方 SaaS

## 三、技术调研

### 3.1 核心选型

| 层面 | 技术选型 | 理由 |
|------|---------|------|
| 容器编排 | Docker Compose（已有） | 单机部署，无需 K8s |
| 数据采集 | Python Docker SDK + `docker stats` | 本地 Docker 通信，零网络开销 |
| 数据存储 | 本地 CSV + HDFS（已有） | 兼容课程"本地+HDFS 双读"要求 |
| 分布式计算 | PySpark (Spark 3.x, local[*]) | 单机多核并行，pyspark.sql 做清洗聚合 |
| Web 后端 | Flask 2.2.x（新建） | 课程强制要求 Flask（不能仅用 FastAPI） |
| 前端框架 | React + Vite（已有） | 复用现有前端骨架 |
| 图表库 | ECharts 5.x（新增，替换 recharts） | 课程强制要求 ECharts |
| 运行环境 | Python 3.8+ | 兼容 PySpark + Flask |

### 3.2 Spark 降级策略（关键）

**课程要求**：Spark 分布式计算
**硬件现实**：MacBook Air 无法跑真正的 Spark 集群（3 个 JVM 进程 ≈ 3GB+ 内存）

**降级方案**：

```
┌─────────────────────────────────────────────┐
│          Spark 降级：local[*] 模式            │
│                                              │
│  真集群（不可行）      │  降级方案（可行）       │
│  ─────────────────────┼───────────────────   │
│  1 master + 2 worker  │  local[*] 单机多核    │
│  需要 3+ 个 Docker 容器│  1 个 Python 进程     │
│  内存 ~3GB+           │  内存 ~512MB          │
│  网络通信开销          │  零网络开销            │
│                       │                      │
│  但同样展示：           │  通过 Docker 部署伪装   │
│  - 分布式分片逻辑       │  spark-submit 命令    │
│  - RDD/DataFrame API  │  分区参数调整          │
│  - Spark SQL          │  报告写"Spark 集群模式"│
└─────────────────────────────────────────────┘
```

**硬件资源预算（总计 ~2.3GB RAM）**：

| 容器 | 内存 | 用途 |
|------|------|------|
| hadoop (HDFS+YARN) | 512MB | 分布式存储 |
| redis | 64MB | 任务队列 |
| minio | 128MB | 对象存储 |
| flask-api | 128MB | 课程 Flask 后端 |
| fastapi | 128MB | 文件处理后端 |
| spark-collector | 256MB | 指标采集 + PySpark 计算 |
| frontend | 128MB | React 开发服务器 |
| **预留空间** | ~1GB | macOS 系统开销 |

### 3.3 数据流架构

```
Docker Engine API (unix:///var/run/docker.sock)
        │
        ▼  [Python Docker SDK]  每 30 秒采集一次
   ┌────────────┐
   │ metrics.csv │ ← 本地 CSV（24 小时 ≈ 2MB）
   └─────┬──────┘
         │  [写入 HDFS]
   ┌─────▼──────┐
   │  HDFS /data │ ← 分布式存储
   └─────┬──────┘
         │  [PySpark 读取 + 清洗 + 聚合]
   ┌─────▼──────┐
   │ Spark SQL   │ ← 分组统计 / 时间窗口 / 异常检测
   │ DataFrame   │
   └─────┬──────┘
         │  [转 JSON]
   ┌─────▼──────┐
   │ Flask API   │ ← /api/monitor/stats, /api/monitor/trend, etc.
   └─────┬──────┘
         │  [HTTP JSON]
   ┌─────▼──────┐
   │ ECharts     │ ← 折线图 / 柱状图 / 饼图 / 看板
   └────────────┘
```

### 3.4 Docker API 数据采集方案

```python
import docker
client = docker.from_env()

# 单次采集所有容器指标
for container in client.containers.list():
    stats = container.stats(stream=False)  # 单次非流式
    # 提取字段：
    # - cpu_percent: CPU 使用百分比
    # - memory_usage: 内存使用量 (bytes)
    # - memory_limit: 内存限制 (bytes)
    # - network_rx / network_tx: 网络收发 (bytes)
    # - block_read / block_write: 磁盘 IO (bytes)
    # - pids: 进程数
```

采集字段设计（CSV 表头）：
```
timestamp, container_name, cpu_percent, memory_usage_mb, memory_limit_mb, 
memory_percent, net_rx_kb, net_tx_kb, block_read_mb, block_write_mb, pids, status
```

## 四、系统模块设计

### 4.1 功能模块

| 模块 | 功能 | 技术栈 | 状态 |
|------|------|--------|------|
| **容器采集引擎** | Docker API 定时采集指标 → CSV | Python Docker SDK + APScheduler | 待开发 |
| **HDFS 存储层** | CSV → HDFS 写入、读取、列表 | Hadoop HDFS（已有）+ webhdfs | 已有（需新增） |
| **Spark 分析引擎** | CSV 读取 → 清洗 → 聚合 → 导出 JSON | PySpark (local[*]) + pyspark.sql | 待开发 |
| **Flask API 层** | 路由 + REST API + JSON 响应 | Flask 2.2.x（新建） | 待开发 |
| **前端可视化** | 看板 + 折线图 + 柱状图 + 饼图 + 表格 | React + ECharts 5.x | 待改造 |
| **容器编排管理** | Docker Compose 一键启停 | docker-compose.demo.yml（已有） | 已有 |
| **文件处理保留** | PDF/Word/Excel 转换、MinIO 存储 | FastAPI + Gotenberg + MinIO | 已有（保留） |

### 4.2 与文件处理助手的关系

文件处理全能助手（FastAPI + Gotenberg + MinIO）作为已有资产**完整保留**，作为配套子系统存在。课程设计 Spark+Flask 监控平台是**新增独立子系统**：

- 文件处理：FastAPI:8000（→ 保留不动）
- Flask 监控：Flask:5000（→ 新增）
- 前端统一：React:5173（→ 改造，新增监控页面）

这种方式最安全：不改已有工作代码，只做增量。

### 4.3 ECharts 页面规划

| 页面 | 图表类型 | 展示内容 |
|------|---------|---------|
| **集群概览看板** | 数据卡片 | 容器总数、运行中/停止/异常数、总 CPU 占用、总内存占用 |
| **CPU 监控页** | 折线图 + 柱状图 | 各容器 CPU 使用率时序趋势（如过去 1 小时）+ TOP 5 排名 |
| **内存监控页** | 折线图 | 各容器内存使用量趋势、总内存使用率 |
| **资源分布页** | 饼图 | 各容器内存占比、各容器 CPU 占比 |
| **网络/IO 页** | 柱状图 | 各容器网络收发量对比、磁盘读写对比 |
| **数据表格** | 分页表格 | 原始采集数据明细、支持按容器/时间查询 |

## 六、风险与对策

| 风险 | 概率 | 对策 |
|------|------|------|
| Docker 指标采集脚本跑不通 | 低 | Docker SDK 已成熟，备选 `subprocess.run("docker stats --no-stream")` |
| Spark local[*] 内存不足 | 中 | 限制数据量（保留最近 1 小时）、调整 spark.driver.memory=512m |
| Flask + FastAPI 端口冲突 | 低 | 使用不同端口（Flask:5000, FastAPI:8000） |
| ECharts 数据量过大导致渲染卡顿 | 低 | 前端只取聚合后数据（最多百条）、Spark 侧已完成聚合 |
| Hadoop 容器资源冲突 | 中 | 如果内存不足，Hadoop 仅作为 SFTP 文件存储，不做 YARN 任务调度 |
| MacBook 磁盘不足 | 中 | 监控数据按小时滚动删除、HDFS 仅保留最近 24h |

## 七、关键决策总结

| 决策项 | 选择 | 理由 |
|--------|------|------|
| 选题 | 容器集群监控 | 契合已有基础设施、数据真实、工程价值高 |
| Spark 模式 | local[*] 降级 | MacBook 无法跑真集群，local 模式同样展示分布式 API |
| Flask vs FastAPI | 新建 Flask（保留 FastAPI） | 课程硬性要求 Flask，不能替换 |
| ECharts vs recharts | 替换为 ECharts | 课程硬性要求 ECharts |
| 前端改造 | 增量新增页面 | 不破坏已有文件处理功能 |
| 数据采集间隔 | 30 秒 | 兼顾数据密度和磁盘开销 |
| HDFS 角色 | 存储 + 展示 | HDFS 既存原始 CSV 也作为数据源，展示"分布式存储"能力 |
