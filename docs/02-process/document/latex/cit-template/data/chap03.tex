\chapter{系统分析}

本章在前文政策背景、市场调研和行业痛点的基础上，对 CulCloud 平台进行需求分析。分析对象限定为两个端侧：用户端与管理端。用户端面向普通文件处理者，负责资料上传、目录整理、文件预览、格式转换和 PDF 页面处理；管理端面向系统维护者，负责观察任务、日志、服务健康和历史分析结果。本章重点说明系统应完成什么、数据应如何被记录、哪些边界暂不纳入当前版本，为第 4 章系统总体设计提供依据。

\section{用户角色与用例分析}

\subsection{用户端角色}

用户端角色在代码中对应 \texttt{user}。该角色的主要目标是以云盘方式组织个人资料，并在同一平台内完成常见文件处理。用户端需要能够上传本地文件、创建文件夹、移动文件、按类型筛选、打开预览、提交格式转换任务、查看转换历史、进入 PDF 编辑室并导出处理后的 PDF 文件。用户端不直接访问 MinIO、Redis 或 Gotenberg，而是通过前端 API 客户端调用 FastAPI 接口，由后端完成对象写入、任务创建和结果返回。

\subsection{管理端角色}

管理端角色在代码中对应 \texttt{admin}。该角色不重复用户端的文件编辑操作，而是观察系统运行状态。管理端需要查看当前文件规模、任务成功率、失败任务、近期事件、队列长度、服务健康和历史分析样本。管理端第一屏必须使用 FastAPI 的实时接口聚合当前业务状态；Spark 与 ECharts 相关历史样本只能作为离线分析结果，不与实时指标混用。前端通过角色状态控制管理菜单可见性，后端敏感接口通过角色校验返回访问结果。

图 \ref{fig:chap03-user-case} 给出了系统用例关系。该图只保留用户端与管理端两个参与者，核心用例按文件管理、文件处理、PDF 编辑和运行观察组织，以减少图中交叉线条。用户端用例之间存在自然的包含关系，例如文件预览与格式转换均依赖文件选择；管理端运行观察包含任务统计、日志统计和服务健康读取。

\section{功能需求分析}

\subsection{核心功能需求}

\subsection{业务边界}

当前版本定位为最小可用的云端资料处理平台，重点保证单用户文件管理、轻量转换、PDF 页面处理和管理端运行观察。系统暂不实现多人协同编辑、跨设备冲突合并、企业级权限矩阵、文件版本回滚和长期审计归档。这些能力需要更复杂的关系数据模型、权限模型和审计策略，超出当前原型的主要验证范围。明确边界后，后续设计可以集中在文件对象、任务状态、运行日志和分析样本之间的一致性上。

从优先级看，文件上传、列表刷新、预览、格式转换、PDF 导出和任务状态查询属于 P0 需求，必须在系统主链路中稳定可用；目录整理、类型筛选、历史任务和管理端实时观察属于 P1 需求，用于提升系统完整度和可观察性；离线历史分析、质量热力图和历史转换桑基图属于 P2 需求，主要体现大数据分析能力。这样的优先级划分能够避免把历史分析样本误认为实时业务必需条件，也能保证核心文件处理链路优先完成。

从输入输出边界看，用户端输入主要包括本地文件、目标目录、目标格式、PDF 页面配置和批注对象；系统输出主要包括文件列表项、预览内容、任务编号、任务终态、结果下载地址和错误原因。管理端输入不是人工录入数据，而是读取系统运行过程中已经产生的文件、任务、日志和健康状态。该边界说明管理端图表的真实性依赖后端接口，而不是依赖前端写死的显示数值。

\section{非功能需求分析}

系统非功能需求包括可用性、稳定性、可维护性、安全性和可复现性。可用性要求页面具备加载、空状态、成功、失败和可恢复提示；稳定性要求长任务具有可查询状态，基础依赖异常时能够返回结构化错误；可维护性要求前端视图、API 客户端、后端路由和领域服务边界清晰；安全性要求不暴露对象存储内部地址，不采集与文件处理无关的敏感信息；可复现性要求 PM2、Docker Compose、接口探测和端到端用例可以重复执行。

对于可用性，系统不能只要求页面能够打开，还要要求操作链路能够闭合。例如上传完成后应能在文件列表中看到对象，转换完成后应能获得结果入口，PDF 导出完成后应能打开新文件。对于稳定性，系统需要把长任务的中间状态显式暴露给前端，避免用户无法判断任务是否仍在运行。对于可维护性，前端页面不能直接拼接对象存储内部地址，后端也不能把格式转换细节散落在多个路由中，而应通过领域服务统一处理。

对于安全性，系统的核心要求是最小暴露和路径清洗。文件名、目录前缀和结果地址都可能来自用户输入，后端必须统一规范化处理；下载与预览应通过 API 代理，避免把内部对象存储端口、桶名和临时对象路径直接暴露给浏览器。对于可复现性，测试不仅要覆盖页面操作，还要覆盖容器状态、进程状态、接口返回和自动化用例，使后续验证人员能够按固定顺序复查系统。

\subsection{数据模型与数据流}

图 \ref{fig:chap03-er-model} 给出了文件对象、任务对象和事件日志之间的概念关系。一个文件对象可以产生多个预览缓存、转换任务或 PDF 处理任务；一个任务最多生成一个结果产物；任务状态变化会产生事件日志。该关系用于约束后续设计：文件、任务、日志三者需要能够通过对象名或任务编号追溯，而不能只停留在前端按钮状态上。

从数据流角度看，用户端操作首先进入 FastAPI 路由，路由调用领域服务写入 MinIO 或 Redis；当任务完成后，产物重新进入对象存储，状态和日志进入 Redis；管理端读取 FastAPI 聚合接口形成实时运行视图，历史分析页读取 Flask/Spark 结果形成离线分析视图。图 \ref{fig:chap03-data-flow} 用需求层数据流表达了这一关系。

数据流分析还要求区分四类状态。第一类是浏览器临时状态，例如当前选中的文件、预览弹窗是否打开和 PDF 工作区缩放比例；第二类是对象存储状态，例如原始文件、预览缓存和转换产物；第三类是运行状态，例如任务进度、失败原因和近期事件；第四类是历史分析状态，例如 Spark 聚合后的文件类型分布和错误热力图。只有第二类和第三类能够直接反映当前业务结果，第四类只能用于历史分析，第一类则不应作为验收依据。

\section{需求量化指标}

为便于测试和管理端观察，需求分析阶段需要定义若干可计算指标。设用户可见文件对象集合为 $O=\{o_1,o_2,\ldots,o_n\}$，对象大小为 $size(o_i)$，则用户端容量需求指标为：
\begin{equation}
  S=\sum_{i=1}^{n} size(o_i).
  \label{eq:req-storage-size}
\end{equation}
式 \ref{eq:req-storage-size} 用于约束首页和管理端容量统计口径：目录占位对象、预览缓存和临时转换文件不应混入用户原始资料容量。

设等待、处理中、成功和失败任务数分别为 $Q$、$P$、$C$、$F$，则实时任务总量为：
\begin{equation}
  T=Q+P+C+F.
  \label{eq:req-task-total}
\end{equation}
式 \ref{eq:req-task-total} 用于限定管理端第一屏的任务规模来自当前业务任务集合，而不是来自 Spark 历史样本。由此可以进一步得到成功率和失败占比，为第 4 章运行指标设计提供基础。

\section{可行性与合规边界}

\subsection{技术可行性}

React、FastAPI、MinIO、Redis、Gotenberg、Docker Compose、PM2、Spark 与 ECharts 均为成熟技术。项目代码已经具备前端视图、后端路由、对象存储、任务状态、预览服务、转换服务和分析展示基础，因此继续围绕主链路完善需求具有可行性。异步任务通过 Redis 状态与后端后台任务解耦，能够避免长时间转换阻塞普通接口；对象存储通过统一对象名前缀表达目录结构，能够满足当前文件管理需求。

\subsection{安全与合规边界}

系统只保存文件名、对象路径、大小、类型、任务状态和必要日志，不主动采集与文件处理无关的个人敏感信息。日志记录任务状态、操作类型和错误原因，但不记录文件正文内容。文件删除、移动和重命名均由用户主动触发，预览缓存与转换产物应与原文件隔离。若 Redis 或持久化卷不可用，近期日志和任务历史可能不完整，该边界需要在测试和系统状态中明确说明。

\section{本章小结}

本章从用户端与管理端两个角色出发，明确了功能需求、非功能需求、数据字典、概念数据模型、数据流和量化指标。需求分析的核心结论是：CulCloud 应围绕文件对象、任务状态、事件日志和分析样本建立可追溯链路。第 4 章将在此基础上进一步说明系统分层架构、业务流程、算法、公式、状态流转和部署结构。
