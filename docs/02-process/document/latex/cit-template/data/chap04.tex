\chapter{系统总体设计}

本章在系统分析基础上给出 CulCloud 的总体设计，包括系统功能设计、业务流程设计、数据结构设计和部署结构设计。

\section{系统功能设计}

\subsection{功能模块划分}

为了明确 CulCloud 前后端数据交换边界与协作职责，系统在顶层设计上进行了清晰的功能模块划分，将核心业务凝聚为六大模块。表 \ref{tab:function-modules} 展示了各模块的主要功能与数据来源。

在业务分工与数据流向上，这六大模块高度协同。个人首页充当用户看板，前端定期请求相关接口以呈现最新的存储与任务指标；我的云盘对接 MinIO 对象存储，实现目录树的动态解析；转换中心与 PDF 编辑室通过异步队列调用 Gotenberg 和本地处理器完成文档加工；管理驾驶舱与系统状态则汇总由 Spark 聚合的运营数据，并配合健康检查与日志接口，实时反馈集群运行效能，从而形成了逻辑分明、数据流清晰的系统功能版图。

\subsection{用户端模块}

用户端包含个人首页、我的文件、转换中心和 PDF 工作台。个人首页展示真实指标；我的文件负责云盘组织；转换中心负责文件格式转换；PDF 工作台负责阅读、批注和页面整理。

\subsection{管理端模块}

管理端包含任务监控、系统状态 and 数据分析驾驶舱。任务监控用于查看转换状态和失败原因，系统状态用于观察服务健康，数据分析驾驶舱用于展示文件类型分布、转换趋势和质量指标。

\section{业务流程设计}

\subsection{文件上传与整理流程}

用户上传文件后，前端调用文件上传 API，将文件写入对象存储。系统根据当前云盘路径记录对象名称，并在页面中展示文件所在路径。用户可通过拖拽或“移动到”按钮将文件移动到指定文件夹。

\subsection{文件预览流程}

预览模块根据文件类型生成 PDF、图片、文本、HTML、音频或视频预览内容。CSV、Markdown 和 TXT 直接生成浏览器可展示内容；Office 文件优先通过转换为 PDF 的方式预览；暂不支持的类型给出明确提示。

\subsection{文件转换流程}

当用户在转换中心提交格式转换请求后，前端向 FastAPI 后端发送指令。后端任务追踪器立即生成全局唯一的任务标识，将状态设为排队中（queued）并推入 Redis 队列。这一过程使得高并发下的转换任务能够以有序、非阻塞的方式进行处理。部署在后台的 Celery 工作进程通过轮询从队列中捞取任务，将状态变更为处理中（processing），并拉取源文件分发给 Gotenberg 等后台转换容器执行。转换成功后，工作进程将生成产物写回 MinIO 并将任务状态转移至完成（completed）；若转换失败，则捕获异常并将状态转为失败（failed）。在此期间，前端利用延时短轮询（polling）机制定期查询最新状态，动态更新历史处理记录列表，直到任务进入终态后终止轮询。

\section{数据库与对象结构设计}

\subsection{文件对象结构}

系统文件实体以对象路径为核心，同时记录文件名、文件大小、最近修改时间和内容类型等属性。其中 \texttt{object\_name} 承担云盘路径职责，文件夹通过路径前缀和 \texttt{.keep} 占位对象表示。

\subsection{任务对象结构}

系统采用 Redis 的哈希结构（HASH）来存储每个转换任务，其以格式为 \texttt{task:task\_id} 的键名作为唯一标识。该结构记录了任务类型、当前状态、创建与更新时间、结果路径等字段。为防止用户频繁提交请求导致 Redis 内存无节制增长，系统为每个任务哈希键设置了 24 小时的生存时间（TTL），过期后自动清理，这不仅保障了 Redis 的物理存储空间不会过载，也极大地提升了系统的整体检索响应速度。

\subsection{日志对象结构}

操作日志在 Redis 中通过两个数据结构来支撑审计与遥测。针对近期事件的快速展现，系统维护了一个最近日志列表（logs:recent），使用列表结构并配合循环裁剪机制（LTRIM），只保留最多 5000 条最近操作以控制内存；针对跨时间段的检索，系统维护了一个按时间排序的有序集合（logs:timeline），通过有序集合（ZSET）存放序列化后的 JSON 日志记录，以日志生成的时间戳作为分数值，支持管理驾驶舱对指定时间段的操作日志进行毫秒级的高效范围查询，为系统运行状态的实时诊断和安全审计提供了强有力的数据支撑。

\section{部署结构设计}

\subsection{PM2 本地演示结构}

本地演示优先使用 PM2 管理前端和后端进程，避免临时终端关闭导致服务中断。PM2 进程定义应明确工作目录、启动命令、端口和环境变量。

\subsection{Docker Compose 依赖结构}

系统采用 PM2 与 Docker Compose 混合部署的架构治理策略。高频迭代且需热重载的前端与 Flask 分析服务由 PM2 进程管理器托管，以提升开发调试效率；而 Redis、MinIO、Gotenberg 等环境复杂的基础服务则统一使用 Docker Compose 进行容器化治理。在 Docker 虚拟网络（如 \texttt{culcloud\_net}）中，API 容器和 Gotenberg 容器通过内网虚拟网络实现内网互通，API 容器可以直接通过容器名称进行低延迟的内部调用。为了保证数据持久性，MinIO 存储桶与 Redis 的状态数据通过挂载卷（Volumes）与宿主机物理目录绑定。这种有状态服务与无状态服务的精细化分类治理，不仅简化了容器编排复杂度，更显著增强了系统在极端重启测试下的数据鲁棒性。

\section{本章小结}

本章完成了系统总体设计，明确了功能模块、业务流程、数据结构和部署结构。后续详细实现将围绕这些设计展开，并通过测试验证文件夹、预览、转换和日志链路是否真实跑通。
