\chapter{系统分析}

本章从用户角色、功能需求、非功能需求和可行性四个方面分析 CulCloud 平台，为后续总体设计和详细实现提供依据。

\section{需求分析}

\subsection{用户角色分析}

系统用户分为学生用户、教师/评委和管理员三类。系统用户权限设计基于精细的角色划分，聚焦于普通学生角色（在代码中表示为 user）与管理员角色（在代码中表示为 admin）的业务边界。学生用户（即 demo\_user）关注上传、分类、预览、转换和 PDF 编辑，侧重完成个人的文件上传、多级移动与分类检索、即时预览、格式转换和在线 PDF 工作台编辑等业务；教师/评委关注系统是否具备真实功能和可演示证据；管理员（即 admin）关注任务队列、失败任务、系统健康和数据驾驶舱，侧重查看系统全局性能驾驶舱（Analytics.tsx），对后台转换任务状态进行实时监控（SystemStatus.tsx）和处理。系统在前后端实施精细的访问控制，前端基于角色动态隐藏管理菜单，后端 API 路由拦截器通过 get\_current\_role 对敏感接口进行角色校验，非管理员请求时返回 403 响应，保障安全隔离。

\subsection{功能性需求}

系统需要支持文件上传、文件夹管理、文件移动、文件分类、文件预览、格式转换、PDF 批注、页面整理、任务历史、失败提示和管理端数据分析。所有用户可见功能应尽量接入真实接口，避免静态数据造成演示偏差。

\subsection{非功能性需求}

系统应具备较好的可用性、可维护性和演示稳定性。前端页面需要清晰展示加载、成功、失败和空状态；后端接口需要返回可解释错误；长任务需要支持状态查询；日志与历史记录需要在浏览器刷新和 PM2 重庆后尽量保持。

\section{可行性分析}

\subsection{社会可行性分析}

课程项目中的文件资料数量多、类型杂、版本变化频繁，学生对于统一整理和快速预览工具具有现实需求。CulCloud 面向课程大作业场景，不涉及复杂商业化协作，功能边界清晰，适合作为教学演示型平台。

\subsection{技术可行性分析}

React、FastAPI、MinIO、Redis、Celery、PDF 渲染和 Spark 分析均为成熟技术。项目已经具备文件上传、对象存储、预览、转换、PDF 编辑室和管理驾驶舱的基础代码，因此继续补齐文件夹移动、预览矩阵和测试链路具备可行性。在全栈架构选择上，系统前端采用 React 框架结合 TypeScript 静态类型语言，而后端使用高性能的 FastAPI 异步框架，并配合 Python 的 Celery 异步任务队列，这一技术组合具有高度的合理性。针对 PDF 转换等计算密集且耗时较长的异步任务，系统引入了 Celery 分布式任务队列，并使用高性能 Redis 内存数据库作为任务缓冲池（Message Broker），实现主服务与后台转换任务的彻底解耦。当用户发起格式转换请求时，FastAPI 向 Redis 写入任务信息并向前端返回任务标识（Task ID），便可立即结束请求以缩短 API 响应时间；后台 Celery 工作进程则按序拉取任务并调用 Gotenberg 服务进行格式处理，有效缓解了高并发转换请求对服务器造成的瞬时 CPU 压力，在技术层面确保了系统的强健性。

\subsection{演示可行性分析}

系统可通过 PM2 启动前端和后端服务，也可通过 Docker Compose 启动完整依赖。演示时优先选择已验证的 P0 功能链路，包括上传文件、移动到文件夹、预览文件、提交转换、查看历史和打开管理驾驶舱。为了在有限的答辩演示中保障“即开即用、重启不丢状态、快速重置”的特性，并满足评委的审核诉求，系统采用利用 PM2 进程管理器（托管前端与分析服务）与 Docker Compose（托管 Redis、MinIO、Gotenberg 容器）组成的混合部署架构。利用 Docker Compose 编编基础设施，消除了本地环境配置的繁琐性；状态数据写入持久化卷，保证了重启不丢状态。前端与分析服务由 PM2 托管，具备秒级热重载能力，可在评委提出临时微调时快速修改生效，避免构建镜像的漫长等待，确保演示的高敏捷性。

\section{数据安全与合规分析}

\subsection{最小必要采集}

系统只保存文件名、对象路径、大小、类型、任务状态和必要日志，不主动采集与课程演示无关的个人敏感信息。页面展示也以文件处理结果为主，不扩展社交化或推荐类数据。系统并不采集用户隐私信息，仅在后端记录操作者的角色、上传时的元数据大小、文件名、操作时间戳。所有持久化数据均用于支持云盘的核心功能，系统内部不设立任何用户画像、社交关系网络或基于内容特征的智能推荐算法，从源头上杜绝了敏感信息泄露和数据滥用的安全与合规风险。

\subsection{文件删除与缓存隔离}

文件删除、重命名和移动均由用户主动触发。预览缓存和转换产物需要与原文件隔离，避免预览生成过程覆盖用户上传内容。在物理删除设计上，当用户点击“删除文件”时，系统调用 FastAPI 后端的 delete\_file 接口，在 MinIO 中彻底物理移除原对象，并同步清除与该文件绑定的 Gotenberg 转换临时缓存，并清理数据库与 Redis 中的临时状态。原文件、转换产物与任务缓存三者同步物理擦除，使得系统在物理层面上没有任何冗余副本残留，防止了数据残留与物理存储空间的泄露。

\subsection{日志留痕边界}

日志用于实验追踪和异常定位，应记录任务状态、操作类型和错误原因，但不记录文件正文内容。若 Redis 或持久化卷不可用，系统需要在文档中说明日志可能丢失的边界。为满足安全审计要求，用户的每一次上传、移动、转换、删除操作都在后端通过 log\_event 函数实时写入 Redis timeline（基于有序集合 ZSET 结构，如 logs:timeline）。记录的信息包括时间戳、事件类型（如 upload、convert 等）、操作人角色、目标文件名和执行结果，并基于 Redis 内存限制，在日志记录函数中对 logs:recent 队列通过 ltrim 进行裁剪，将最近事件日志维持在最多 5000 条的滑动留痕边界内，防止内存无限膨胀。

\section{本章小结}

本章明确了 CulCloud 的用户角色、核心需求、可行性和合规边界。系统建设重点不是扩大功能数量，而是保证云盘、转换、预览、PDF 编辑和日志分析这些主链路真实可用。
