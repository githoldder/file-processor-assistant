\chapter{系统测试}

本章围绕 CulCloud 的核心业务链路进行测试，重点验证文件上传、目录整理、文件预览、格式转换、PDF 页面导出、任务状态、日志记录和管理端观察是否能够形成可复现闭环。测试结果既包括浏览器端界面结果，也包括后端自动化测试、前端类型检查、运行接口探测和端到端角色路由验证。

\section{测试层次与边界}

系统测试按环境层、接口层、业务层、联动层和异常层展开。环境层验证 Docker Compose 与 PM2 管理的服务是否在线；接口层验证 FastAPI、Flask Analytics 和健康检查是否返回结构化结果；业务层验证上传、预览、转换和 PDF 导出是否形成产物；联动层验证用户端操作是否进入任务统计、日志统计和管理端实时视图；异常层验证不存在的资源、非白名单格式和依赖异常能否被解释。表 \ref{tab:chap06-test-levels} 给出了测试层次。

从系统边界看，单纯打开页面不能证明服务链路完整，因此测试需要同时保留命令行结果和浏览器端结果。命令行结果用于证明服务进程、容器依赖、接口返回和自动化用例可重复；浏览器端结果用于证明用户能够完成实际操作。两类证据共同覆盖“系统是否运行”和“业务是否闭环”两个问题。

环境层测试的重点是确认基础依赖和应用进程处于同一可用窗口内。Docker Compose 负责 Redis、MinIO、Gotenberg 等基础服务，如果这些容器未启动，即使前端页面能够打开，也无法完成任务状态写入、对象保存和文档转换。PM2 负责守护前端、后端或分析服务，若进程状态异常，接口调用和图表刷新也会失效。因此环境层测试先于功能测试执行，只有依赖和进程正常，后续接口层和业务层结果才具有解释意义。

接口层测试的重点是确认系统之间的边界是否真实连通。健康接口用于判断服务是否可访问，文件接口用于判断对象存储链路是否可读，任务统计接口用于判断 Redis 任务集合是否可读，日志统计接口用于判断事件留痕是否可读，分析接口用于判断历史样本是否能被 Flask 服务读取。若这些接口返回结构化 JSON，就说明系统内部边界已经具备可观测性；若只依赖页面结果，则很难定位故障发生在前端、后端还是基础依赖。

联动层测试是本章最重要的验证点。用户端完成上传、转换或 PDF 导出后，系统应产生对象、任务和日志三类变化；管理端第一屏应通过实时接口读取这些变化，而不是通过静态样本显示固定数值。该测试能够证明用户端业务数据与管理端运行观察之间存在真实通路，也能证明历史分析页与实时运行页的口径已经分离。

\section{问题处理与修复验证}

\subsection{文件移动路径边界}

文件移动测试中重点检查根目录、同名目录和子目录移动边界。系统通过 \texttt{folders.py} 对目标前缀进行规范化处理，并拒绝会造成目录循环的操作。合法移动通过 MinIO 复制对象到新前缀，再删除旧对象完成。该处理保证了前端目录视图与后端对象名前缀一致。

\subsection{CSV 与 Markdown 预览边界}

CSV 与 Markdown 预览容易受到编码、行列长度和 HTML 渲染安全影响。系统在后端预览服务中将 CSV 组织为表格化 HTML，将 Markdown 转换为独立 HTML 响应，再由前端预览框展示，避免用户上传内容直接进入主页面 DOM。测试结果表明，结构化表格和 Markdown 文本均能形成可读结果。

\subsection{任务历史状态边界}

早期状态字段可能出现 \texttt{success} 与 \texttt{completed} 混用的问题。当前前端读取任务接口时兼容后端状态，并以任务详情中的 \texttt{result\_url} 和 \texttt{error} 作为结果判断依据。这样即使页面刷新，历史任务仍可从 Redis 状态中恢复，不依赖浏览器临时变量。

\subsection{PDF 导出文字与坐标边界}

PDF 导出测试中重点关注批注框、文本位置和中英文混排。后端转换服务已加入 CJK 字体加载，导出时使用页面尺寸和前端画布尺寸进行坐标映射。导出后的 PDF 能保留文本和矩形框，说明前端批注对象到后端 PDF 坐标之间的映射链路可用。

\subsection{管理端联动边界}

管理端联动测试关注用户端业务增量是否进入实时运行视图。测试方法是在用户端完成上传、转换或 PDF 导出后，立即读取 \texttt{/api/v1/tasks/stats}、\texttt{/api/v1/logs/stats} 和 \texttt{/api/v1/logs/timeline}，再观察管理端第一屏指标与近期事件是否刷新。该测试能够区分实时运行数据和历史分析样本：实时指标来自 FastAPI 聚合接口，会随业务操作变化；历史分析页来自 Spark 输出，只用于较长时间窗口的样本分析。

该边界测试的判定标准不是图表数值越大越好，而是数值来源是否可信、变化是否可解释。若用户上传一个文件，文件列表和日志时间线应出现对应记录；若提交一次转换，任务统计中等待、处理中或成功数量应发生变化；若 PDF 导出成功，结果产物应进入对象存储并形成完成事件。只有这些变化能够被 API 和管理端同时观察到，才能说明系统完成了从用户操作到运行观察的闭环。

\subsection{稳定性与后续改进}

当前测试表明系统已具备文件管理、文件预览、格式转换、PDF 编辑和管理端观察的核心能力。仍需在后续版本中加强的部分包括大文件分片上传、多用户权限隔离、高并发转换任务、容器重启后的恢复策略以及 Spark 分析链路的持续增量更新。上述内容属于生产级强化方向，不影响当前系统作为课程场景下云端资料处理平台的核心功能验收。

因此，本轮测试结论采用“已满足核心流程、保留生产强化空间”的判定方式，既确认当前功能可用，也明确后续优化边界。

从测试覆盖角度看，当前测试已经覆盖了前端类型、后端路由、角色访问、接口健康和核心业务链路，但仍需要在后续补充更长时间窗口的运行稳定性测试。例如连续上传多个大文件、并发提交多个转换任务、重启 Redis 后检查任务历史恢复能力、重启 MinIO 后检查对象列表恢复能力、关闭 Gotenberg 后检查转换失败提示。上述测试能够进一步验证系统从可运行原型向长期运行平台演进时的可靠性。

\section{本章小结}

本章从测试环境、功能测试、命令行验证、问题处理和结果分析几个方面验证了 CulCloud。测试结果说明，系统能够完成上传、预览、转换、PDF 页面导出、状态记录、角色隔离和管理端观察等关键流程，达到了系统设计目标。
